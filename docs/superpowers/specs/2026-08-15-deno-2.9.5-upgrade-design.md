## 2. Driver and scope

**Driver:** routine cadence. No deadline, no blocking feature, no CVE. Optimises for a clean, maintainable end state.

**In scope:** a pure version bump, 2.7.14 → 2.9.5, in a single hop. Every existing trex fork patch carries forward unchanged in intent. Two deliberate structural changes:

1. Adopt the Deno monorepo's `libs/eszip` 0.135.0 and retire the standalone eszip fork.
2. Drop the `v8::Locker` patch from the rusty_v8 fork and delete the dead code in `crates/base` that was its only consumer.

**Out of scope**, all deferred to separate follow-up work:

- Dropping any other fork patch on the grounds that upstream has caught up.
- Adopting upstream's new `deno_inspector_server` 0.31.0 in place of `crates/base/src/inspector_server.rs`.
- The QuickJS backend that `deno_v8` now offers.
- Any behaviour change to worker_threads, node:http, or the OS sandbox.

## 3. Findings that shaped this design

Each was verified against the actual git tags, not inferred.

**F1 — `v8` is now a facade crate.** At 2.9.5 the workspace declares `v8 = { package = "deno_v8", version = "0.2.0", path = "./libs/deno_v8" }`. `libs/deno_v8` wraps `rusty_v8` (`v8` **150.4.0**) and can alternatively select a QuickJS backend. Our fork targets rusty_v8 147.4.0 and must move to 150.4.0.

**F2 — `v8::Locker` is dead code in this repo.** `crates/base/src/runtime/mod.rs:2041` declares `trait JsRuntimeLockerGuard` under `#[allow(dead_code)]`; its sole call site at `mod.rs:1714` is commented out. `assert_isolate_not_locked` (`mod.rs:502`) is likewise `#[allow(dead_code)]`. Nothing in the deno fork references `v8::Locker` either. The architecture moved to thread-pinned isolates (`crates/base/src/runtime/thread_utils.rs:6`, `mod.rs:1157,1296`).

Upstream rusty_v8 150.4.0 has **no** `src/locker.rs`, so the patch would otherwise need rebasing across three V8 major versions to serve no consumer.

**F3 — the cppgc/isolate guards are load-bearing.** The fork commit `4506b1c` bundles two independent patches. Separate from Locker, `src/isolate.rs` (+317) and `src/cppgc.rs` (+41) add null guards for the `RustObjConcrete` layout. These back trex-runtime's `d4fe5ee7` (null isolate in V8 interrupt callbacks) and `18d88638` (isolate lifecycle management). They stay.

**F4 — the standalone eszip upstream is dead.** `denoland/eszip`'s last tag is `v0.109.0` — exactly what our fork sits on. Development moved into the Deno monorepo, now `libs/eszip` 0.135.0. Keeping the standalone fork means maintaining an orphaned 0.109 against ever-moving `deno_graph`/`deno_npm`/`deno_ast` pins, with no upstream to pull from.

**F5 — `deno_canvas` split out of `deno_image`.** 2.9.5 adds `ext/canvas` (`deno_canvas` 0.119.0); `runtime/Cargo.toml` now depends on both it and `deno_image` (0.23.0 → 0.33.0).

**F6 — three ext crates only *appear* to have been dropped.** `deno_broadcast_channel`, `deno_console` and `deno_url` left upstream's `[workspace.dependencies]` block at 2.9.5, but the crates still exist under `ext/` at *identical* versions (0.216.0, 0.222.0, 0.222.0). `crates/base/Cargo.toml:14,18,127` and `deno/Cargo.toml:45` still use them. Their pins do not change.

**F7 — the fork's patches fall into two classes, and the risk is the opposite of what file size suggests.**

| File | Upstream 2.7.14 | Upstream 2.9.5 | trex fork | Class |
|---|---|---|---|---|
| `_http_server.ts` | 136 | 136 | 1252 | wholesale replacement; upstream blob **byte-identical** across the range |
| `worker_threads.ts` | 1421 | 2335 | 503 | wholesale replacement (`44b71cdc9` gutted it −1410, `0e676bbde` added 491 trex lines) |
| `http2.ts` | 4680 | 5585 | 4680 | **patch already retired** at 2.7.14 — upstream fixed it (`1d19d73a`) |
| `01_require.js` | 1560 | 3500 | 1533 | true patch, on a file upstream more than doubled |
| `https.ts` | 337 | 725 | 205 | true patch (a strip) |
| `os.ts` | 425 | 356 | 379 | true patch |

Wholesale replacements are mechanically trivial to carry — they do not merge, they overwrite. The genuinely hard rebase is `01_require.js`.

**F8 — staging through 2.8.3 would not have split the work.** Churn across the five hottest fork-patched files is ~70/30 front-loaded: 5,053 changed lines in 2.7.14 → 2.8.3 versus 2,174 in 2.8.3 → 2.9.5. Staging would buy a bisect point, not two easier hops. Decision: single hop.

## 4. Invariants (acceptance criteria)

1. The V8 startup snapshot builds and loads, with and without `--features trex`.
2. Every behaviour fixed in the last six commits on `develop` still holds: cert store → Deno cert store (`60f811b1`), inspector WS 1001 drain (`429920c7`), user-worker exit reason on shutdown race (`5b8b3e2b`), OTel exporter init from CLI flags (`788b0872`), `trex_core` in the snapshot (`7b1266f4`).
3. Existing eszip artifacts still load. The format is a compatibility surface with deployed functions, not an internal detail.
4. No fork is added to the chain; one is removed.

## 6. Approach: layered, with two de-risking spikes

Two risks are structural rather than mechanical, and both can be tested cheaply before the expensive work starts. Everything else in this upgrade is a known quantity — version bumps and a patch rebase whose difficulty is measured in §3/F7.

### Spike A — rusty_v8 `v150.4.0` (½–1 day)

Branch `supabase-v150.4.0` off `v150.4.0`. Port **only** the cppgc/isolate null guards from `4506b1c`, plus `284e41f` (arm64) and `c7aa72c` (release assets publish to the triggering tag), and the `.gn` / `BUILD.gn` / `build.rs` bits those require. Drop `src/locker.rs`.

- **Pass:** builds standalone on x86_64 and aarch64; release assets publish; `deno_core` 0.410 links against it.
- **Fail:** the `RustObjConcrete` layout moved again under V8 150. Fallback: re-derive the guards from the crash they were written for, using `#91` and `#103` as the specification.

### Spike B — eszip 0.135 format compatibility (½ day, parallel to A)

Throwaway binary against 2.9.5's `libs/eszip`: parse existing `supabase/edge-runtime-test-eszip` fixtures; round-trip an eszip produced by the current 2.7.14 build; confirm `EszipV2Module`, `EszipV2Modules`, `EszipV2SourceSlot`, `EszipV2::from_graph`, `EszipRelativeFileBaseUrl` are reachable, applying the visibility patch if not.

- **Pass:** existing artifacts parse. Proceed.
- **Fail:** escalate as a product decision — either a migration path through `crates/deno_facade/eszip/migrate.rs`, or hold eszip at 0.109 with hand-bumped deps as the documented fallback.

Spike B is genuinely throwaway — a probe whose output is an answer. Spike A is not: if it passes, its branch *is* the real `supabase-v150.4.0` and C1 is simply its completion (CI, release assets, both arches verified). Neither spike blocks the other; the deno-fork rebase starts only after both report.

Approaches rejected: *straight layered without spikes* (saves a day, but surfaces both structural risks a week in, when backing out is expensive); *big bang* (one failure mode indistinguishable between V8, eszip, and `deno_core` 0.410 API drift).

## 7. Execution

### C1 — rusty_v8 fork → `supabase-v150.4.0`
Completes Spike A's branch: verify both arches, wire up CI, publish release assets for x86_64 and aarch64 (`.devcontainer/install.sh` and CI consume them).

### C2 — deno fork → `trex-v2.9.5`
Gated on C1. Branch off `v2.9.5`, rebase the 8 trex commits. The `http2.ts` patch was retired at 2.7.14 — do not resurrect it.

*Wholesale replacements — carry the fork's file verbatim, no merge:*
- `_http_server.ts` — upstream 136 lines, byte-identical across the range; the fork's 1252-line version drops straight in.
- `worker_threads.ts` — take the fork's 503-line version as-is. Upstream's grew to 2335; we deliberately do not track it.

*True patches — three-way merges, ascending difficulty:*
`console.ts` → `os.ts` → `ext/net/ops_tls.rs` → `libs/npm_installer/flag.rs` → `libs/resolver/deno_json.rs` → `runtime/{worker,web_worker,snapshot}.rs` → `https.ts` → `libs/resolver/{factory,workspace}.rs` → `ext/node/lib.rs` → `ext/telemetry/lib.rs` → `libs/core/modules/map.rs` → `01_require.js`.

*Add-only, no conflicts:* `ext/base_rt/*`, `ext/ext_os/*`.

Then a 9th commit: the eszip visibility patch applied to `libs/eszip`, and `libs/deno_v8`'s `rusty_v8` dependency pointed at C1's branch.

**Gate:** `cargo check --workspace` inside the fork.

### C3 — trex-runtime dependency wiring
`Cargo.toml`: apply the §9 version delta; add `deno_canvas = "0.119.0"`; leave the three F6 crates unchanged. Retarget all 28 deno `[patch.crates-io]` entries to `trex-v2.9.5`, `v8` to `supabase-v150.4.0`, `eszip` to the deno fork branch; delete the standalone eszip patch line. `deno/Cargo.toml` → `version = "2.9.5"`.

Check `rust-toolchain.toml` (currently 1.92.0) against 2.9.5's MSRV — the 2.7.12 upgrade bumped it.

### C4 — re-sync the vendored `deno/` crate against `v2.9.5`
File-by-file three-way merge against upstream `cli/`. Layout is stable across the range: only `cli/node_compat_shim.rs` and `cli/rt_desktop/` are new, and neither is mirrored here. `deno/runtime/errors.rs` gets special attention — every prior upgrade touched it.

### C5 — compile fixes, in dependency order
`deno/` → `crates/` → `ext/`. Fix compile errors only; log behaviour questions rather than acting on them.

Two carve-outs that are not ordinary error-chasing:

**The snapshot list.** `deno_canvas` must be inserted at the *identical index* in both `crates/base/build.rs` and `crates/base/src/runtime/mod.rs`. The build.rs comment is explicit that a mismatch yields `ExtensionSnapshotMismatch` — a runtime panic, not a compile error. Highest-risk mechanical step in the upgrade.

**The Locker deletion.** Remove from `crates/base/src/runtime/mod.rs`: `use deno_core::v8::Locker` (57), `LockDebugState`, `LOCK_DEBUG_STATES` (126), `isolate_debug_key` (131), `log_locker_event` (137), `assert_isolate_not_locked` (502), `JsRuntimeLockerGuard` and both impls (2041–2092), and the commented call site (1714). Keep `cleanup_js_runtime`, dropping only its now-orphaned first three lines. Land as one self-contained commit so it can be reverted independently.

Predicted hot spots for the rest, ranked:

| Area | Why |
|---|---|
| `crates/deno_facade/eszip/*`, `graph.rs`, `metadata.rs`, `module_loader/standalone.rs` | eszip 0.109 → 0.135 |
| `crates/base/src/inspector_server.rs` | `deno_core` 0.410 inspector API |
| `deno/runtime/errors.rs` | new/renamed error variants — touched in every prior upgrade |
| `deno/npm/**`, `deno/resolver.rs`, `deno/args/**` | `deno_npm` 0.59→0.69, `deno_config` 0.97→0.107, `deno_resolver` 0.78→0.88 |
| `deno/graph_util.rs`, `crates/deno_facade/graph.rs` | `deno_graph` 0.107→0.110, now `default-features = false` upstream |
| `crates/fs/impl/*` | `deno_fs` 0.157→0.167 (`virtual_fs.rs` took 270 lines at 2.7.12) |
| `ext/{runtime,os,workers,ai,env,event_worker}` | `deno_core` op-macro changes |
| anything using `deno_semver` | 0.9 → 0.10 is a semver break |

### C6 — version strings, CI, docs

| File | Change |
|---|---|
| `.env:2` | `DENO_VERSION=2.9.5` |
| `.github/workflows/ci.yml:26` | branch trigger `deno2.7.14` → `deno2.9.5` |

## 8. Validation

### D0 — baseline, before anything changes
On `develop` @ 2.7.14, record to files: `GIT_V_TAG=0.1.1 cargo build`, `cargo build --release` (the release profile is where `crates/base/build.rs` actually runs the snapshot), and a full `./scripts/test.sh`. Note tests already skipped or failing so a pre-existing skip is not later misread as a regression.

### D1 — test matrix

| Invariant | Check |
|---|---|
| Snapshot builds and loads | `cargo build --release` with and without `--features trex`; assert the snapshot is used, not silently skipped |
| eszip artifacts load | `crates/base/tests/eszip_migration.rs` + `supabase/edge-runtime-test-eszip` fixtures |
| node:http path | node:http server, WebSocket upgrade, Express — exercises the `_http_server.ts` replacement |
| worker_threads | the trex 503-line implementation under its existing tests |
| Cert store | `DENO_TLS_CA_STORE`; root cert store → Deno cert store |
| Inspector | debugger attach + WS 1001 close-frame drain on shutdown |
| OTel | exporter init from CLI flags — `deno_telemetry` took 1,043 lines of upstream churn; most likely silent regression |
| Worker lifecycle | user-worker exit reason when it loses the shutdown race |
| Web platform | `Deno.serve`, `fetch`, node:http2 client |
| trex-specific | per-worker console, OS sandboxing |

### D2 — performance
`b7c7367a` re-enabled the snapshot specifically to cut user-worker cold start. Measure cold start against D0 — a snapshot that builds but no longer helps passes every functional test.

### D3 — load
k6 suite (`k6/`, `.github/workflows/k6.yml`).

### D4 — downstream
`--features trex` is never exercised by this repo's CI (the `trex_core` stub, `Cargo.toml:284-289`), so the parent `OHDSI/trex` build is the only place a `trex_core` break surfaces. Coordinate before merging.

### D5 — rollback
Revert `Cargo.toml` + `Cargo.lock` on `deno2.9.5`, which retargets `[patch.crates-io]` back to `trex-v2.7.14` / `supabase-v147.4.0` / the standalone eszip fork. The only change that is not a pin revert is the Locker deletion — one commit, revertible on its own.
