# Deno 2.9.5 Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move `trex-runtime` from Deno 2.7.14 to 2.9.5 in a single hop, retiring the standalone eszip fork and the dead `v8::Locker` patch along the way.

**Architecture:** Four repositories in a dependency chain. Two forks are rebased onto new upstream tags (`p-hoffmann/rusty_v8` → `v150.4.0`, `p-hoffmann/deno` → `v2.9.5`), a third fork (`p-hoffmann/eszip`) is retired because its upstream is dead, and then `trex-runtime` is rewired to point at the new branches and fixed up. Work is strictly bottom-up: each layer must compile standalone before the layer above it is touched. Two cheap spikes run first to test the only two structurally risky assumptions.

**Tech Stack:** Rust 1.92.0, Cargo workspaces with `[patch.crates-io]` git overrides, Deno / `deno_core` 0.410, V8 via the new `deno_v8` 0.2.0 facade over rusty_v8 150.4.0, eszip 0.135.

**Spec:** `docs/superpowers/specs/2026-08-15-deno-2.9.5-upgrade-design.md`

## Global Constraints

- Target Deno version: **2.9.5**. Single hop from 2.7.14; do **not** stage through 2.8.x.
- Rust toolchain: `1.92.0` (`rust-toolchain.toml`). If 2.9.5 requires higher, bump it and say so — do not silently pin lower.
- Work happens on branch `deno2.9.5` in `trex-runtime` (already created; the spec is committed there).
- **Never force-push** `trex-v2.7.14`, `supabase-v147.4.0`, or `supabase-v0.109.0-edge-runtime-2.7.14`. They are the rollback path.
- Every existing trex fork patch carries forward **unchanged in intent**. Do not "improve" a patch while rebasing it. The single exception is the Locker patch, which is dropped (Task 10).
- `deno_broadcast_channel` (0.216.0), `deno_console` (0.222.0) and `deno_url` (0.222.0) are **unchanged** at 2.9.5 despite leaving upstream's `[workspace.dependencies]` block. Do not bump or remove them.
- The `http2.ts` patch was retired at 2.7.14 (`1d19d73a`). Do not resurrect it.
- Out of scope, do not do opportunistically: adopting `deno_inspector_server`, the QuickJS backend, dropping any other fork patch, any behaviour change to worker_threads / node:http / OS sandbox.

## A note on testing in this plan

This is a dependency upgrade, not a feature. There is almost no new behaviour to test-drive, so classic red-green TDD does not apply to most tasks. The discipline that replaces it:

**Task 1 captures a baseline before anything changes, and that baseline is the test oracle for the whole plan.** Every later task's verification is a diff against it. A task is not done because it compiles — it is done when its named check produces the same result as the baseline, or a deliberately better one.

Two tasks do get real tests written first: Task 2 (a probe whose entire output is a pass/fail answer) and Task 11 (where the failure mode is a silent runtime panic that no existing test would catch).

```rust
use std::env;
use std::path::PathBuf;

#[tokio::main]
async fn main() {
    let mut failures = 0usize;
    let mut successes = 0usize;

    for arg in env::args().skip(1) {
        let path = PathBuf::from(&arg);
        let bytes = match std::fs::read(&path) {
            Ok(b) => b,
            Err(e) => {
                println!("READ-ERR {arg}: {e}");
                failures += 1;
                continue;
            }
        };

        let reader = futures::io::BufReader::new(futures::io::Cursor::new(bytes));
        match eszip::EszipV2::parse(reader).await {
            Ok((eszip, loader)) => {
                // Driving the loader to completion is what actually validates
                // the body sections, not just the header.
                match loader.await {
                    Ok(_) => {
                        let specifiers = eszip.specifiers();
                        println!("OK {arg}: {} modules", specifiers.len());
                        successes += 1;
                    }
                    Err(e) => {
                        println!("BODY-ERR {arg}: {e}");
                        failures += 1;
                    }
                }
            }
            Err(e) => {
                println!("PARSE-ERR {arg}: {e}");
                failures += 1;
            }
        }
    }

    println!("---");
    println!("parsed_ok={successes} failed={failures}");
    if failures > 0 {
        std::process::exit(1);
    }
}
```

- [ ] **Step 1: Write the failing test first**

This is the one place in the upgrade where a real test earns its keep. Create `crates/base/tests/snapshot_extension_parity.rs`:

```rust
//! The V8 startup snapshot is created in build.rs from one extension list and
//! consumed in runtime/mod.rs from another. deno_core requires the two to have
//! identical names in identical order, or it raises ExtensionSnapshotMismatch
//! at runtime -- a panic no functional test would otherwise catch.
//!
//! This test compares the two lists as source text so it fails at `cargo test`
//! rather than when a worker boots in production.

use std::fs;

fn extension_names(source: &str, start_marker: &str) -> Vec<String> {
    let start = source
        .find(start_marker)
        .unwrap_or_else(|| panic!("marker not found: {start_marker}"));
    let tail = &source[start..];
    let end = tail.find("];").expect("unterminated extension list");
    tail[..end]
        .lines()
        .filter_map(|line| {
            let line = line.trim();
            if line.starts_with("//") || line.starts_with('#') {
                return None;
            }
            // matches `deno_web::deno_web::lazy_init(),` -> "deno_web"
            let name = line.split("::").next()?.trim();
            if name.is_empty() || !name.chars().next()?.is_ascii_lowercase() {
```

## Task 8a: Fix the per-worker OTel attributes TypeId bug

Added 2026-08-18 at the user's request. Found by Task 6's review (finding I-2). **Pre-existing — not a regression from this upgrade; the same bug is present at 2.7.14.**

**The bug:** `OpState` is TypeId-keyed, and two structurally identical structs live in two different crates.

| Role | Site | Type |
|---|---|---|
| Producer | `crates/base/src/runtime/mod.rs:1364` — `op_state.put(...)` | `base_rt::RuntimeOtelExtraAttributes` |
| Consumer | fork `ext/telemetry/lib.rs:1822` and `:2370` — `state.try_borrow::<...>()` | `deno_otel_attrs::RuntimeOtelExtraAttributes` |

Different TypeIds, so `try_borrow` always returns `None` and **the fork's per-worker OTel attributes never fire.**

**Why the fix belongs here and not in Tasks 4-7:** the fork side is already correct — `ext/base_rt` (package `deno_otel_attrs`) exists precisely to be the shared type crate, and `ext/telemetry` consumes it properly. The duplicate is trex-runtime's own `crates/base_rt`. ## Task 8b: Consume upstream rusty_v8 artifacts instead of the fork's

Added 2026-08-18. Follows the audit of the rusty_v8 fork's necessity.

**Finding:** `src/binding.cc`, `.gn`, and `BUILD.gn` on `supabase-v150.4.0` are **byte-identical** to upstream `v150.4.0` (`b5d145d1`, `5f9df22a`, `5d7b05e9`). The fork's only surviving source change is `src/cppgc.rs` (live guards) plus a `build.rs` sysroot fix — both **Rust**, compiled locally on every build.

Therefore the compiled V8 static library and the generated `src_binding` are equivalent to upstream's, and `RUSTY_V8_MIRROR` can point at upstream's releases. The `[patch.crates-io] v8` entry still points at the fork, because the cppgc guards are load-bearing.

**What this buys:** upstream publishes `aarch64-apple-darwin` and `x86_64-apple-darwin` assets, so **macOS builds stop needing `V8_FROM_SOURCE=1`** — the single largest environment cost in this upgrade. It also removes any dependence on the fork's ~2h CI to produce artifacts, and eliminates the Linux-only asset limitation.

**Interfaces:**

- Produces: a build that resolves V8 prebuilts from upstream on every platform.
